# 2026-10-24 – M2c MCP interface for AI agents

## Done
- **Access tokens** (`internal/auth/apitokens.go`, table `access_tokens`):
  - Personal tokens `gpat_…` (256 bit). Only the SHA-256 is stored, the token is shown once with ready-made client configuration.
  - Expiry 7/30/90/365 days, at most 10 per user, last use and address recorded.
  - Created under Profile › Access Tokens in a full 2FA session with a recent re-authentication; a security notice goes out by mail.
  - Revoked by the user (one or all), by administrators (Users › Edit), and automatically by a password change or reset, a 2FA reset, a role change, "log out everywhere" and the corresponding CLI commands; deleted with the user.
- **Scopes through the capability system:**
  - `db.User.CapLimit` limits a request's capabilities to the token's scopes, and `auth.Can` honors it. Every existing check in the content service therefore applies unchanged.
  - Scopes: `content:write` (default), `content:publish`, `media:upload`, `terms:manage`. A scope only grants what the role already has.
  - No scope grants `unfiltered_html`, others' content, deleting or administration.
- **Settings › Writing:** "AI agents (MCP)" switch, off by default; turning it on needs a re-authentication.
- **`/mcp`** (`internal/mcpserver`), using the official Go SDK in stateless mode with JSON responses:
  - Tools: `get_site_info`, `list_posts`, `get_post`, `list_terms`, `create_post`, `update_post`, `create_category`, `upload_media`, `list_media`. `tools/list` only shows what the token's scopes allow (one cached server per scope set).
  - Markdown (goldmark, GFM) or HTML. Content is always sanitized; code blocks keep their `language-*` class.
  - Agents read published content and their own; `update_post` changes only the given fields and needs `expected_modified` (optimistic locking against edits in the admin).
  - Without `content:publish`, "publish" becomes "pending" (with a note), and published posts cannot be changed.
  - Uploads: images and PDF only, as base64, through the normal media pipeline (type sniffing, metadata removal, sizes).
- **Audit:** every entry made with a token carries `via: mcp`, the token id and name, and the client address.
- **Tests:**
  - Unit tests (tokens, scopes, audit).
  - Admin HTTP tests (switch, token pages, CSRF, re-auth, revocation).
  - MCP tests with the SDK client against `httptest`: tools per scope, life cycle, sanitizing for administrator tokens, foreign content, uploads, all guards, rate limits.
  - E2E step: switch on, create a token in the UI, agent writes a draft, revoke → 401.
- **Tried with Claude Code** (`claude -p` with `--mcp-config`) against a throwaway copy of the site: it read the site and the categories and wrote a release draft with a list and a fitting category; the audit log names the token.
- **Mobile:** the token table becomes labelled cards on narrow screens.

## Decisions
- **Personal access tokens instead of OAuth 2.1:**
  - They work with every MCP client (Bearer header) and keep the attack surface small: no authorization server, client registration or redirect handling.
  - OAuth stays possible later (noted in PLAN).
- **Official MCP Go SDK** instead of an in-house JSON-RPC implementation: protocol versions, schema generation and conformance are maintained upstream.
- **Stateless mode:** no server-side sessions to exhaust; GET (standalone SSE) answers 405, which the spec allows.
- **The SDK's localhost DNS-rebinding check is disabled.** A reverse proxy on the same host would trip it. The Origin/Sec-Fetch-Site checks and the mandatory Bearer token cover DNS rebinding.
- **One body limit** (10 MB upload as base64 plus JSON) with at most 4 requests in progress. A separate small limit for non-upload calls would need the body to be parsed first.
- **While switched off,** `/mcp` is handled by the public site like any unknown URL.
- **Uploads through MCP only accept images and PDF.** An agent misled by prompt injection must not turn the site into a download host for archives or packages.
- **Agents never see or change other users' drafts,** even with an administrator's token: a token is a narrower credential than the session.

## Security review
An independent review agent checked the token life cycle, scoping, the endpoint guards, the SDK integration and DoS limits; every finding was reproduced with a test and fixed with a regression test (`TestReviewFindings`, `TestLimiterBounded`, `TestTokensRevokedOnRoleAndPasswordChange`).

| Finding | Severity | Fix |
|---|---|---|
| The SDK still accepts JSON-RPC batches for old protocol versions: one request created 200 posts, bypassing the per-request limit | Medium | Batches are refused (400) before the SDK sees them |
| `list_posts` searched the content of other users' password protected posts (prefix search could read it out) | Medium | For others' posts only titles are searched unless the post has no password |
| Content size was only bounded by the 13 MB body limit (heap peaks near 900 MB with 4 parallel calls) | Medium | Content at most 1 MB, excerpt 64 KB, title 1000 bytes, 100 tags, checked before conversion |
| `parent` accepted other users' private pages (and returned their slug in the link) | Low | Parent pages and featured images must be published or the user's own |
| A title-only update re-filtered the kept content of an administrator's own post (removing embeds) | Low | `Save` only filters submitted fields; kept content was filtered when it was written |
| `upload_media` with alt text stored the file, then failed without `content:write` (duplicates on retry) | Low | Refused before storing |
| Limiter maps were scanned on every request above 50 000 keys; the first failure from every IPv6 /64 was audited | Low | Pruning at most once a minute, new keys refused while full; extra /48 limit; auditing per /48 |
| Changing one's own password or a role change left tokens working (a demoted user could not even see them) | Low | Both revoke all tokens of the user |
| `list_media` listed files of other users' drafts | Info | Only the user's own files and those of published posts |

Checked and holding: token generation, hashing, single display, expiry, per-user limit, CSRF and re-authentication on the token routes, revocation paths, capability intersection (no unfiltered HTML, no foreign or deleted content), foreign drafts/private/trashed posts invisible by id, slug and URL, protected content hidden, cookies ignored, Origin/Sec-Fetch-Site checks, no CORS, generic errors, no URL fetching, audit tagging.
